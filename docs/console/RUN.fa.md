# اجرای GreFlow Console

این بسته برنامهٔ اجرایی GreFlow Console با backend واقعی است.
دامنهٔ تست‌ها و محدودیت‌های نسخه در `TEST-RESULTS.md` ثبت شده‌اند. دادهٔ اولیهٔ سرور،
رمز پیش‌فرض و نتیجهٔ شبیه‌سازی‌شده ندارد. هیچ نصب‌کننده‌ای خودکار تانل‌ها را restart نمی‌کند.

## ویندوز x64

بستهٔ `greflow-console-windows-amd64.zip` را استخراج کنید. PowerShell:

```powershell
.\greflow-console.exe --data "$env:LOCALAPPDATA\GreFlow\data"
```

نشانی `http://127.0.0.1:8787` را باز کنید. در اجرای اول فقط رمز پنل و تکرار آن را وارد
کنید؛ مستقیم وارد پنل می‌شوید. نام کاربری پیش‌فرض `admin` است و در بخش بازشونده قابل
تغییر است. کد راه‌اندازی و TOTP وجود ندارد. رمز حداقل ۸ نویسه است؛ حساب‌های قبلی حفظ می‌شوند.
برای شروع با مرورگر، `Start-GreFlow.ps1` و برای توقف `Stop-GreFlow.ps1` آماده‌اند.
خروج از مرورگر برنامه را متوقف نمی‌کند. توقف برنامه، پایش و هشدار مرکزی را متوقف می‌کند؛
تانل‌های سرور و timerهای systemd مستقل می‌مانند.

کلید اصلی با Windows DPAPI به حساب فعلی ویندوز وابسته است و در
`%APPDATA%\GreFlow\console-master.key` ذخیره می‌شود. کپی دیتابیس به حساب دیگر،
به‌تنهایی کلیدهای SSH را بازیابی نمی‌کند. قبل از انتقال سیستم، بکاپ رمزگذاری‌شده دارای
کلید بسازید. ARM64 ویندوز در این بسته پشتیبانی/تست نشده است.

## لینوکس amd64 و arm64

بستهٔ متناسب با معماری را استخراج کنید و checksum را بررسی کنید:

```bash
sha256sum -c SHA256SUMS
sudo bash install-console.sh
sudo systemctl enable --now greflow-console
```

نصاب فقط فایل‌ها و service پنل را نصب می‌کند. دیتابیس در `/var/lib/greflow-console`
و کلید با دسترسی 0600 و مالک سرویس در `/etc/greflow-console/master.key` است.
این فایل جدا از بکاپ دیتابیس نگهداری شود. این مدل حفاظت فایل سیستم است، نه HSM/KMS.
در اولین مراجعه رمز پنل را تعیین کنید؛ حساب دوم یا کد نصب لازم نیست.

دسترسی عمومی باید با HTTPS باشد. نمونهٔ Nginx در بسته است؛ دامنه و مسیر گواهی را
با مقادیر واقعی خود تنظیم کنید و `GREFLOW_ORIGIN` را در
`/etc/greflow-console/environment` دقیقاً برابر origin مرورگر قرار دهید.
هدر Origin و CSRF بررسی می‌شوند؛ قرار دادن آدرس اشتباه باعث رد درخواست تغییر می‌شود.
پنل روی loopback گوش می‌دهد؛ موتور GRE نیازی به اجرای پنل با root ندارد.

Compose از سورس:

```bash
mkdir -p data keys
sudo chown 10001:10001 data keys
chmod 700 data keys
export GREFLOW_ORIGIN=https://your-console-domain
docker compose -f packaging/compose.yml up -d --build
```

داده و کلید mountهای جدا هستند. Compose/GRE در این محیط ویندوزی اجرا نشده‌اند.

## اتصال SSH و شناسایی

نصب ابزار مدیریت برای سرور SSH خودکار است. بستهٔ کامل کنسول را همراه پوشهٔ `helpers`
استخراج کنید؛ این پوشه فایل‌های Linux amd64 و arm64 و manifest صحت فایل را دارد.
سرور مقصد نیازی به دانلود اینترنتی ندارد. با افزودن سرور، یک عملیات آماده‌سازی پایدار
ثبت می‌شود: اتصال SSH، بررسی معماری، انتقال فایل، بررسی SHA256 و نسخه، نصب اتمیک
و شناسایی فقط‌خواندنی. فایل موجود سازگار دوباره نصب نمی‌شود؛ فایل ناسازگار هم بی‌اجازه
بازنویسی نمی‌شود. CLI، config، firewall و سرویس‌های تانل تغییر نمی‌کنند.
برای سرورهای قبلی «آماده‌سازی خودکار» را اجرا کنید. دکمهٔ «شناسایی فقط‌خواندنی»
همچنان فقط می‌خواند و هیچ نصب یا تغییر تنظیماتی انجام نمی‌دهد.

در صفحهٔ سرورها، آدرس و «پسورد SSH» یا «کلید خصوصی SSH» را انتخاب کنید. نام کاربری
پیش‌فرض root و پورت 22 است؛ در تنظیمات بازشونده قابل تغییرند. کلید را می‌توان paste یا از
فایل انتخاب کرد؛ کلید رمزدار با passphrase هم پشتیبانی می‌شود. همهٔ اطلاعات ورود با
AES-GCM در خزانه ذخیره می‌شوند و در خروجی API یا localStorage بازگردانده نمی‌شوند.

«بررسی اتصال» ورود SSH و وجود helper را بدون نصب یا تغییر سرور می‌سنجد. پس از مشاهدهٔ
نتیجه، «افزودن و آماده‌سازی خودکار» را بزنید. اثرانگشت دستی لازم نیست: اولین کلید میزبان ذخیره می‌شود
(اعتماد در اولین اتصال، نه تأیید مستقل). تغییر بعدی کلید همان میزبان اتصال را متوقف می‌کند.
اثر انگشت در جزئیات فنی نتیجه برای مقایسهٔ اختیاری دیده می‌شود.

نصب خودکار با root مستقیم انجام می‌شود؛ برای کاربر غیر root به مجوز sudo بدون رمز
برای نصب نیاز دارد و هیچ مجوز sudo جدیدی ایجاد نمی‌کند. اگر حساب فقط مجوز محدود
dispatch دارد، ابزار را ابتدا توسط مدیر با `install-agent.sh` نصب کنید.
root دستور ثابت helper را مستقیم اجرا می‌کند و به نصب sudo نیاز ندارد. برای مدیریت روزمره با حساب غیر-root،
مجوز محدود زیر را با `visudo` تنظیم کنید؛ پسورد SSH به sudo یا خط فرمان فرستاده نمی‌شود:

```sudoers
greflow-admin ALL=(root) NOPASSWD: /usr/local/bin/greflow-agent dispatch
```

شناسایی فقط‌خواندنی است. تمام configهای معتبر default/named را نشان می‌دهد، حتی اگر
متوقف باشند. آدرس‌های واقعی و machine-id برای تشخیص ثبت تکراری استفاده می‌شوند.
شناسایی هیچ config قدیمی را apply نمی‌کند. config ناسالم باعث خطای مستقل شناسایی است.

گزارش زنده و قابل دانلود در «گزارش اتصال و عملیات» شامل مرحله، زمان، وضعیت، کد خطا
و کد خروج است. خطاهای DNS، TCP، هویت SSH، ورود، معماری، بسته، نصب و شناسایی
جدا گزارش می‌شوند. stderr خام اتصال و نصب منتشر نمی‌شود و رمز یا کلید در گزارش نیست.
اگر انتقال قطع شود نتیجه نامشخص است؛ آماده‌سازی مجدد ابتدا فایل موجود را بررسی می‌کند
و به‌صورت اتمیک از بازنویسی جلوگیری می‌کند. گزارش‌ها در دیتابیس کنسول ذخیره می‌شوند؛
نگهداری نتیجه‌ها تابع تنظیمات پایش (پیش‌فرض ۳۰ روز) است.

## عامل خروجی HTTPS/mTLS

این روش به آدرس HTTPS قابل دسترس از ایران نیاز دارد؛ localhost ویندوز کافی نیست.
پنل یک listener جدا و مستقیم TLS برای عامل‌ها دارد. نمونهٔ اجرای دستی:

```bash
greflow-console --data /var/lib/greflow-console \
  --key-file /etc/greflow-console/master.key \
  --listen 127.0.0.1:8787 --origin https://your-console-domain \
  --agent-listen 0.0.0.0:9443 --agent-url https://your-agent-domain:9443 \
  --tls-cert /path/to/fullchain.pem --tls-key /path/to/privkey.pem
```

گواهی listener باید برای دامنه معتبر و مورد اعتماد سیستم میزبان باشد. TLS termination
در reverse proxy برای این پورت مجاز نیست؛ TCP pass-through قابل استفاده است.
پنل نباید از هدرهای قابل جعل برای اعتماد به گواهی کلاینت استفاده کند.

از «عامل خروجی» یک میزبان و توکن ۱۰ دقیقه‌ای بسازید. روی میزبان، دستور enrollment
نمایش‌داده‌شده را اجرا کنید و توکن را در prompt مخفی وارد کنید. توکن در URL یا command
history قرار نمی‌گیرد. سپس `systemctl enable --now greflow-agent` را اجرا کنید.
کلید Ed25519 روی میزبان تولید می‌شود؛ پنل فقط CSR دریافت می‌کند. گواهی ۳۰ روزه است
و عامل در هفتهٔ آخر تمدید می‌کند. لغو عامل، همهٔ گواهی‌ها و توکن‌های آن را باطل می‌کند.
اگر عامل تا پس از انقضا خاموش بماند، enrollment تازه لازم است.

## افزودن و مدیریت تانل

افزودن تانل، plan فقط‌خواندنی ایران را اجرا می‌کند. IPv4 دو طرف باید مستقیماً روی
میزبان‌ها باشد، نام/رابط/شبکهٔ /30 و endpoint pair تکراری نباشد. تک‌دستور خارج برای
**helper نصب‌شده از همین بسته** تولید می‌شود؛ دانلودر یا URL انتشار ساختگی ندارد.
ابتدا خروجی واقعی خارج را بررسی و سپس اعمال ایران را تأیید کنید.

دکمهٔ بررسی، شواهد سرویس، GRE peer، قوانین و TCP مقصد را جدا دریافت می‌کند. UDP و
بازهٔ TCP نیازمند تست برنامه‌اند. TCP موفق هیچ‌گاه تأیید کاربر را ثبت نمی‌کند. فقط بعد از
تست کلاینت واقعی «ثبت تأیید کلاینت» را بزنید. شواهد پس از ۱۸۰ ثانیه قدیمی می‌شوند.

ویرایش پورت فقط اختلاف قوانین متعلق به تانل را تغییر می‌دهد؛ رابط GRE بازسازی نمی‌شود.
انتقال فعلاً برای تک‌پورت TCP روی همان IP ایران است: تست مقصد جدید، journal دو config،
حذف/افزودن محدود، readback و تست اتصال جدید. در شکست، برگشت best-effort انجام می‌شود.
`rolled_back` و `rollback_failed` متفاوت‌اند. اتصال‌های قبلی conntrack ممکن است تا reconnect
روی مقصد قبلی باقی بمانند؛ هیچ flush عمومی یا selective deletion خودکاری انجام نمی‌شود.

اگر عملیات قطع شد، پنل `uncertain` نشان می‌دهد و آن را خودکار تکرار نمی‌کند. journal
میزبان در `/var/lib/greflow/console-journal` است. عملیات `recover` از API برای بازیابی
mappingهای journal قابل استفاده است؛ در اختلاف با تغییر CLI، بازیابی خودکار رد می‌شود.
برای lifecycle قطع‌شده، config و kernel باید دستی بررسی شوند. بازسازی کورکورانه ممنوع است.

## زمان‌بندی، پایش و هشدار

بررسی دوره‌ای و restart با unitهای اختصاصی `greflow-console-ID.service/.timer` روی خود
میزبان اجرا می‌شوند. فاصله ۱ تا ۱۰۰۸۰ دقیقه و jitter حداکثر ۱۵ ثانیه است. systemd اجرای
هم‌زمان یک timer را جلوگیری می‌کند. خروجی در journal میزبان است. منطقهٔ زمانی برای نمایش
ثبت می‌شود؛ timer فاصله‌ای است، نه cron بر اساس ساعت دیواری.

پایش مرکزی در تنظیمات پیش‌فرض خاموش است. با فعال‌سازی، discovery/probe واقعی در صف
قرار می‌گیرند. هشدار تلگرام نیازمند ثبت token/chat ID و فعال‌سازی صریح ارسال است.
صف اعلان تکرار وضعیت را حذف می‌کند؛ خطای ارسال با backoff تا هشت تلاش ثبت می‌شود.
خاموشی پنل باعث توقف اعلان مرکزی می‌شود. بازیابی شرطی با ۳ شکست متوالی، cooldown
ده‌دقیقه‌ای و سقف ۳ تلاش در ساعت قابل انتخاب است؛ پیش‌فرض انتخاب نشده است. موفقیت TCP
از restart به علت شکست ping جلوگیری می‌کند. حالت نگهداری هر برنامه اجرای آن را متوقف
می‌کند. پنجرهٔ روزانهٔ نگهداری با منطقهٔ زمانی انتخابی، از جمله عبور از نیمه‌شب، قابل ثبت است.
همهٔ برنامه‌های بازیابی یک سقف مشترک ۶ تلاش در ساعت و فاصلهٔ حداقل ۵ دقیقه روی میزبان دارند.
۵۰ نتیجهٔ اخیر روی میزبان ذخیره و پس از شناسایی در پنل خوانده می‌شوند. اجرای بعدی فقط از
خروجی JSON نسخه‌های سازگار systemd خوانده می‌شود؛ نبود آن «نامشخص» است.
این منطق به تست systemd واقعی در لینوکس نیاز دارد.

## بکاپ، ارتقا و برگشت

دکمهٔ بکاپ، فایل اختصاصی `GreFlow-YYYY-MM-DD.greflow` می‌سازد: snapshot کامل
حساب‌ها، CA عامل، دسترسی‌ها، کانفیگ‌های شناسایی‌شده، تنظیمات، عملیات و ممیزی.
پوشش فایل، نام محصول و نسخهٔ فرمت دارد و payload با scrypt و AES-GCM و رمز مستقل
حداقل ۱۶ نویسه محافظت می‌شود. فایل قدیمی `.gfb` نیز در بازیابی پذیرفته می‌شود.
TOTP از محصول حذف شده و با بازیابی بکاپ قدیمی دوباره فعال نمی‌شود.

بازیابی preview دارد و فقط روی پنل بدون سرور اعمال می‌شود. snapshot کامل حساب‌ها را
جایگزین می‌کند؛ همهٔ نشست‌ها خارج می‌شوند و باید با حساب موجود در بکاپ وارد شوید.
عملیات queued/running قدیمی uncertain می‌شوند و خودکار اجرا نمی‌شوند؛ توکن‌های enrollment
مصرف‌شده و اعلان‌های pending خاموش می‌شوند. کلیدهای vault برای کلید سیستم جدید بازرمزگذاری
می‌شوند. پس از بازیابی کامل پنل را restart کنید تا CA بازیابی‌شدهٔ عامل‌ها در listener
بارگذاری شود. بکاپ بزرگ‌تر از ۷ MiB از API رد می‌شود؛ برای آن از snapshot خاموش استفاده کنید.

هیچ بازیابی‌ای به کرنل یا configهای میزبان راه‌دور دست نمی‌زند. configهای مشاهده‌شده داخل
snapshot کامل حفظ می‌شوند، اما restore راه‌دور/host-remapping خودکار هنوز در این ساخت نیست.

برای snapshot خاموش کنترل‌پلین، سرویس را متوقف و پوشهٔ داده، کلید اصلی و تنظیمات را با ابزار
بکاپ امن سیستم نگهداری کنید. روی Windows کلید DPAPI به حساب/سیستم وابسته است.
قبل از upgrade دیتابیس، همین snapshot خاموش را بگیرید. هنگام downgrade، دیتابیس
جدید را روی باینری قدیمی باز نکنید؛ باینری قبلی و snapshot همان نسخه را با هم برگردانید.

نصاب لینوکس باینری قبلی پنل را با پسوند `.previous` نگه می‌دارد. uninstall پنل دیتابیس،
کلیدها، عامل‌ها، timerها و تانل‌ها را نگه می‌دارد. حذف helper باید بعد از حذف timerهای
وابسته و لغو دسترسی آن انجام شود؛ اسکریپت نصب پنل چنین پاک‌سازی‌ای انجام نمی‌دهد.

## ساخت و تست از سورس

نیازمند Go 1.27.3، Python 3 و برای تست مرورگر Node + Playwright است.

```bash
go test ./...
go vet ./...
go test -race ./...                    # نیازمند toolchain مناسب C/race
python scripts/package-console.py
node --test web/console/domain.test.cjs
GREFLOW_CONSOLE_BINARY=./dist/greflow-console-linux-amd64/greflow-console \
  node --test web/app/browser.test.cjs
sudo bash tests/integration.sh ./dist/greflow-console-linux-amd64/greflow ./dist/greflow-console-linux-amd64/greflow-agent
```

تست kernel فقط در میزبان لینوکسی مخصوص آزمایش اجرا شود. داده‌های test fixture فقط
در فایل‌های تست هستند؛ `web/console` مرجع نمایشی جداست و در باینری production embed نمی‌شود.

## مدیریت دسترسی و اعتبار شواهد

در تنظیمات، نشست‌های جاری قابل مشاهده و لغو هستند. تغییر رمز همهٔ نشست‌های همان کاربر
را باطل می‌کند. مدیر می‌تواند نقش و محدودهٔ اپراتور/مشاهده‌گر را تغییر دهد یا حساب او را
حذف کند؛ حساب مالک از این مسیر حذف نمی‌شود. کلید SSH از کارت سرور قابل جایگزینی است؛
این کار کلید عمومی را روی سرور نصب نمی‌کند و تا پایان عملیات در صف رد می‌شود.

تأیید کاربر با زمان واقعی، revision و نسل تانل ثبت می‌شود. شناسایی آن زمان را تازه نمی‌کند؛
پس از ۱۸۰ ثانیه قدیمی نشان داده می‌شود. تأیید قدیمی CLI که زمان ندارد، تأیید زنده نیست.
این اعتبار مستقل از شواهد سرویس، GRE و مقصد TCP است.
